## 修复：详情页播放按钮进度串到跳转后的其他视频

**现象**：从视频A详情页点播放→播放中跳转到视频B→返回A详情页，详情页仍是A（正确），但播放按钮进度显示成B的（如00:03），应为A的（08:02）。

**根因**（依据 `monitor/logcat/log1.txt`）：
- `VideoDetailActivity.onActivityResult` 拿到播放器回传的 `last_cid/last_progress`（跳转后为B=38880480778, 3s），**无条件**覆盖到 `this.u.mHistory`，随即 `updateHistoryDisplay` 把B的进度刷到A的播放按钮。
- `requestHistoryForUgc(force=true)` 的 FETCH_FORCE 分支 `else if (lastPlayCid > 0)` 也会把后端返回的任意 `last_play_cid` 写回 `mHistory`，后端滞后为B时同样串片（本次日志后端恰好返回A/raw=0，故未触发，属时序偶然）。

**修复**（`mybv/java/classes/com/bilibili/tv/ui/video/VideoDetailActivity.java`）：
1. `onActivityResult`：仅当 `lastCid == this.u.mCid`（本页自身视频）才覆盖 `mHistory`，否则保留本页历史并打 `ignore foreign video progress` 日志。
2. `FETCH_FORCE`：`else if (lastPlayCid > 0 && lastPlayCid == finalCid)`，仅采纳本页所请求视频的进度。

**构建**：源码在 `mybv/java/classes`，build 流程 javac→dex→baksmali 覆盖 `mybv/smali`→apktool 打包（见 `build.ps1`）。改 .java 即可进 APK。饼爷自己跑 `build.ps1` 验证（四门）。本次未提交/未构建。

**验证线索**：复现后日志应出现 `[ON_RESULT] ignore foreign video progress`，且播放按钮显示 08:02（A的进度），不再为 00:03。

## 分析+修复：自动连播(A放完自动切B)返回后 A 进度仍显示旧值(如00:39)

**现象**：视频A上次进度00:39，A自己播放到结尾并自动连播到B，返回A详情页，播放按钮仍显示00:39。正确逻辑：不论手动还是自动切走其他视频，返回后都应显示 A 的正确进度（已看完）。

**分析结论**：
1. **播放完成"自动上传最终进度"——已有，且在跑**。播放器 `bl/yb.java` 的 `onCompletion`：
   - `c(false, fullDuration, fullDuration)` 上报完整时长；
   - `reportCompleted()` → `zq.a(ctx, avid, cid, sid, epid, playMethod, -1L, 1L, noHistoryPlay)` → `BiliPlayerHistoryService.reportProgress(...)` 打到 `/x/v2/history/report`，`progress=-1`（已看完）。
   → A 的"已看完"已进后端历史。
2. **手动/自动是否单独处理？——否，同一套逻辑**。两条路径共用唯一回传通道 `PlayerActivity.finish()` 回传 last_cid/last_progress → `onActivityResult` → `requestHistoryForUgc(force=true)`。`PlayerActivity.finish()`（smali）无 if(自动连播) 分支；A→B 是同一 PlayerActivity 实例内切换，只有最终从 B 退出才调一次 finish，故 A 的完成态从不通过"回传通道"带回。
3. **返回时能否自动获取后端进度？——能（机制已存在，只是没接上）**。
   - `requestHistoryForUgc` → `/x/player/wbi/v2` 只读**账号级** `last_play_cid`（自动连播后=B），`lastPlayCid != finalCid(A)` 时既不采纳、也未取 A 自身进度 → A 停旧值。
   - 但类内已有 `fallbackLoadHistory()`：调 `/x/v2/view` 读 `data.history.cid/progress`（**按本页视频 cid/avid 回查**），正是 A 自己的进度，且对"已看完"返回 progress=-1。该通道在 FETCH_LOAD 仅 `!playurlSuccess` 时才走，而 `playurlSuccess` 被账号级 last_play_cid>0 提前置真，自动连播场景永远走不到。

**修复**（`VideoDetailActivity.java`，源码改动）：
1. `onActivityResult`：新增诊断日志 `[ON_RESULT] ownCid/mLocalProgressSec/lastCid(fromPlayer)`，便于看 A 旧值是否被正确保留/覆盖。
2. `FETCH_FORCE`：在既有 if-else 前插入分支 `if (lastPlayCid > 0 && lastPlayCid != finalCid)` —— 自动连播场景直接 `fallbackLoadHistory(biliVideoDetail, a2.e())`，按 A 的 cid 回查后端拿到真实进度（已看完=-1），并打 `[FETCH_FORCE] auto-switch ... fall back to per-cid history` 日志。
   - 原 `lastPlayTime<=0 keep-local` 与 `lastPlayCid==finalCid` 两个分支顺延为 else-if，逻辑不变。

**验证线索**（饼爷构建后复现 A→自动连播B→返回）：
- 期望日志：`[ON_RESULT] auto-switch` 一类 + `[FETCH_FORCE] auto-switch: last_play_cid(B)=… != reqCid(A)=…` + `[FETCH_FALLBACK] history cid=A, progressSec=-1`。
- 期望行为：A 详情页播放按钮显示"已看完 / 重新播放"，而非 00:39。
- 未构建，饼爷自己跑 `build.ps1`（四门）。

## 修复（续）：已看完视频返回后仍显示旧进度/视频时长

**现象**（log1.txt 18:37 实测，A=cid40212891299 时长609s）：A 播放完→自动连播B→返回，A 有时停在旧进度175，有时显示成"视频时长609"而非"已看完"。

**根因**：后端对"已看完"用 `last_play_time=-1000`(ms，即-1s) 表示；而 `onCompletion` 还会 `c(false, 609000, 609000)` 上报完整时长。两条竞态路径回查时：
- 后端回 `last_play_time=-1000` → `lastPlayTime=-1`，旧逻辑判 `<=0` 当"无效"→ keep local（停在旧进度175）。
- 后端回 `last_play_time=609000`（完整时长竞态胜出）→ `lastPlayTime=609`，旧逻辑当有效进度 → 显示"视频时长"而非"已看完"。
两条路径都没把"已看完"识别出来。

**修复**（`VideoDetailActivity.java`）：
1. 新增 helper `getDurationForCid(v,cid)`（取分P/视频时长）、`normalizeFinishedProgress(cid, progressSec, dur)`（progress==-1 或 progress>=dur-2 → 归一化为 -1）。
2. `FETCH_FORCE`：新增 `else if (lastPlayTime == -1)` 分支→直接置 `mProgress=-1`（已看完）；`==finalCid` 采纳分支改用 `normalizeFinishedProgress` 归一化。
3. `FETCH_LOAD`、`FETCH_FALLBACK`：取到进度后同样过 `normalizeFinishedProgress`。
4. `updateHistoryDisplay`：`isFinished = progress==-1 || (totalDuration>0 && progress>=totalDuration-2)`，作为显示兜底。

**验证线索**（log1.txt 该场景）：修复后应出现 `[FETCH_FORCE] backend marks finished (last_play_time=-1/-1000), set progress=-1`，且 UPDATE_DISPLAY 显示 progressSec=-1、按钮"已看完/重新播放"。未构建，饼爷自己跑 `build.ps1`。
