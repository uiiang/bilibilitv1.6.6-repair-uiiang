## 详情页播放进度"返回不更新"根因定位 + 修复（已构建通过）

**现象**：详情页原本已有播放进度，进入播放页再返回，按钮进度仍为旧值（正常播放 / 无痕取消 均受影响）。

**根因（两层）**
1. 主因：`BiliVideoDetail.mCid`（`BiliVideoDetail.java:152`）**没有 `@JSONField("cid")`**，而内嵌 `Page.mCid`（:593）有；
   `/x/web-interface/view` 的 `data.cid` 因此不会写入顶层 `mCid`。全仓 `iput mCid` 只有 PGC 转换（`VideoDetailActivity:3228`）
   与 `convertUgcPageToBiliVideoDetail`（仅选集卡片，不替换 `this.u`）⇒ **UGC 详情页 `this.u.mCid == 0`**。
   `onActivityResult` 里 `isOwnVideo = (lastCid == this.u.mCid)` 恒 false ⇒ 播放器回传的权威进度被当外片丢弃。
   PGC 因 `mCid` 有值所以正常 —— 解释"有的视频正常"。
2. 放大器：丢弃后只能吃 `requestHistoryForUgc(force=true)` 的 `/x/player/wbi/v2`，其 `last_play_time` 有同步延迟；
   旧代码只兜住 `<=0`（keep local），没兜住"后端仍是上一次旧非零值"⇒ 旧值回灌。
   且播放 <30s 时 `xj` 的 30s 定时器根本不上报，后端必然旧值 ⇒ 必现。
   原本无进度时后端返回 0 → 显示 00:00，看不出问题，所以只在"已有进度"时暴露。

**三场景实现要点（已写进 docs/无痕播放与返回进度更新分析及修复方案.md）**
- 唯一无痕开关 `ResolveResourceParams.mNoHistoryPlay`；`VideoViewParams.obtainResolveParams()`（smali:1022）返回**活实例**，
  故取消无痕后 `zq`/`zn`/`yb` 立即解禁、`PlayerActivity.finish()` 也立即回传（`mNoHistoryPlay==false` 才 setResult）。
- 无痕（未取消）：`finish()` 不 setResult → `resultCode=RESULT_CANCELED` → 详情页原来整段跳过，后端零写入。
- 回传字段：`last_progress` = `xh.x()`（ms，`getCurrentPosition`）、`last_cid` = `mResolveParams.mCid`，仅 `x()>0` 才回传。

**修复（`VideoDetailActivity.java`，构建源；已 build.ps1 通过）**
1. `onActivityResult` 改为 `requestCode==REQUEST_CODE_PLAY_VIDEO → onPlayerReturned(resultCode,intent)`（不再按 resultCode/模式分叉）。
2. `onPlayerReturned`：命中本页 cid → 写 `mHistory` + 开保护窗 + `updateHistoryDisplay` + 强制校准；
   未命中且 `!sNoHistoryPlayMode` → 兜底刷新 + 校准；仍无痕 → 不动 UI。
   **正常播放与"取消无痕"在此合流**，满足"复用同一套代码"。
3. 新增 `isCidOfCurrentDetail()`：比对 `mCid`、`mHistory.mCid`、`sourcePage.mCid`、`mPageList[].mCid`，绕开 UGC `mCid=0`。
4. 新增 `LOCAL_PROGRESS_PROTECT_MS=15000` + `localProgressProtectedUntilMs`；`requestHistoryForUgc`（$14）与
   `fallbackLoadHistory`（$23）写 `mHistory` 前判断：窗口内且后端不是 `-1` → 跳过覆盖（保留播放器回传值）。
5. 日志：`[ON_RESULT] apply player progress` / `incognito mode, keep detail UI unchanged` /
   `[FETCH_FORCE] stale backend ignored (protect 15000ms)`，便于真机一次定位。

**构建**：`build.ps1` → `mybv.apk` 11,343,778 B（10:51），update.json md5=5224c6a34d3aabaf16e6721cdaa1b9dd。
新方法均编入 smali：`isCidOfCurrentDetail`(6527)、`isLocalProgressProtected`(6649)、`onPlayerReturned`(8971)。

## 进度条时间不一致（右上角比底部少 2-3 秒）根因定位

**结论**：三处进度条是**三套不同时间语义**，右侧预览用的是"预测目标位置"，底部两处用的是"真实播放位置"。

| 进度条 | 实现 | 数据源 | 刷新 |
|---|---|---|---|
| 右上角简易条 | `bl/xi.smali:2434 updateSeekPreview` + `player_seek_preview.xml`（`seek_preview_group`） | `aal` 累加器预测值 `v3` | 仅按键回调（keyDown/repeat） |
| 底部截图条 / 普通条 | `BottomShotMenu.updateProgress` ← `bl/xl$7.smali:94` | `xl.x()`=`getCurrentPosition()` | 每 800ms |
| 底部控制条 | `bl/xi.smali:2917 Q()` → `b(II)`+`a(II)` | `xi.x()`=`getCurrentPosition()`，`isSliding` 时跳过 | 每 800ms |

**关键证据**：`bv0`（原版 1.6.6）**没有** `player_seek_preview.xml`、`initSeekPreview`、`SeekPreview` 任何痕迹 → 右上角预览是修复版新增功能，沿用了原版 `aal` 给底部 SeekBar 用的"预测目标"语义，却按"当前播放位置"展示。

**差值公式**（xi.smali:4410-4630 keyDown / 5051-5170 keyUp）：
Δ = max(a₂·1000, x()+10000) − a₁·1000
- `a₁` = keyDown 时 aal 值（floor(x()/1000) 起算，丢 0~999ms）
- `a₂` = keyUp 时**再累加一次** n·b
- `+10000` 是原版就有的"单击至少跳 10 秒"补偿
⇒ 单击差 ~7-9s；按住 0.7~0.9s 时 b 已涨到 2~3s，正好差 2-3s。预览还在 seek 后继续显示 2000ms（`showSeekPreview`），所以能肉眼对比。

**修复方向（未动代码，待饼爷拍板）**：把 keyDown 算出的 target 存字段，keyUp 直接 seek 该值（不再 `aal.a()` 二次累加、不再重加 ±10s 边界），seek 后立刻回写 preview 与底部时间 → 预览所见即所得。

### 追加：方案 A 只能止血，不根治（12:5x 复核）

**方案 A 修不掉的三条**
1. **松手后预览冻结 2000ms，底部继续走** —— `showSeekPreview` 的 `postDelayed(...,0x7d0)` 只负责隐藏，期间 `Q()` 继续更新底部 ⇒ 差值 = 松手后经过的时间（0~2 s）。**这条是"稳定少 2-3 秒"最可能的直接成因**，与 aal 的 b 值推演叠加。
2. `aal.a(x()/1000)` 的 floor ⇒ 最多再少 999 ms。
3. seek 落点 ≠ `seekTo(target)`（GOP/关键帧对齐）⇒ 底部是实际解码位置，预览是目标值。

**方案 C（根治）要点**
- `isSliding==true`（按住中）→ 预览显示预测 target（keyDown 缓存值，keyUp 直接 seek 它）；
- `isSliding==false` → 预览一律取 `x()`，与底部完全同源：`Q()` 里 `!isSliding` 分支追加"预览可见则 `updateSeekPreview(x, I, false)`"，另在 keyUp 后 `postDelayed(~150ms)` 补刷一次；

**改动载体**：`mybv/java/classes/bl/xi.java`（1506 行，与 smali 同步，build.ps1 直接编译），不必手改 smali。
