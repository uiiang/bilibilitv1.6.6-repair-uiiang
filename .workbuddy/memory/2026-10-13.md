## 进入个性化设置页 crash 修复
- 现象：logcat `AndroidRuntime: FATAL EXCEPTION` — `NullPointerException: ...DrawFrameLayout.setUpDrawable(int) on a null object reference` @ `bl.afm4.onCreateView(afm4.java:240)`（即 `moreActionOkButton.setUpDrawable(...)`，该对象为 null）。
- 根因：新增 `more_action_*` 两 id 在 `R.java` 里硬编码值 `0x7f08026c`/`0x7f08026d`，与 `public.xml` 已有 id **撞车**（`menu_chapter_btn`=0x7f08026c、`menu_scroll_view`=0x7f08026d）；且 `public.xml` 当时未成功写入这两个新 id 的固定定义 → apktool 重打包时资源实际 id 与 `R.java` 错位 → `findViewById` 拿到 null/错视图 → NPE。
- 修复：将两 id 固定到 id 类型区空闲值 `0x7f08026e`/`0x7f08026f`（当前最大值 `menu_scroll_view`=0x7f08026d 之后），同步改 `public.xml` 与 `R.java`；`ids.xml` 仅定义名字不动。三处现一致，重构建后 `findViewById` 能正确命中新按钮。
- 教训：反编译工程新增 id 必须三处（ids.xml/public.xml/R.java）值完全一致且不占用已有 id；以 `public.xml` 中 `type="id"` 当前最大值 +1/+2 取空闲值最稳妥（不要凭记忆写值）。
- 状态：代码层修复完成，需重跑 `build.sh` 重新打包生效（用户此前装的是旧 APK，故进页崩溃）。

## 进入个性化设置页仍崩溃（根因深化：R.java 与 public.xml 系统性 id 错位）
- 现象：修完 more_action 撞车后重构建仍崩，堆栈变 `bl.afm4.onCreateView(afm4.java:316)` —— `menuChapterBtn` 为 null（`findViewById(R.id.menu_chapter_btn)` 未命中）。
- 真因：**`R.java` 的 id 值与 `public.xml`（apktool 打包真实映射）系统性不一致**。`R.java` 的 menu 系列是从 `0x7f0801f8` 起的"连续假设值"，但 `public.xml` 按资源真实分配把 `menu_chapter_btn`/`menu_scroll_view` 放在 `0x7f08026c`/`0x7f08026d`，导致这两个按钮的 `findViewById` 全部错位为 null。more_action 撞车（`0x7f08026c/26d`）只是表象，真正病灶是 R.java 与 public.xml 没对齐。
- 修复：写脚本（`$env:TEMP/align_r.py`）以 `public.xml` 为权威，把 `R.java` 所有内部类（id/layout/drawable/string…）的值对齐到 `public.xml`；原文件备份到 `$env:TEMP/R_java_align_backup.java`。脚本报告仅 3 处差异被修正：`id.menu_chapter_btn`(0x7f080201→26c)、`id.menu_scroll_view`(0x7f080202→26d)、`string.subtitle_size`(0x7f0c0192→191)。对齐后两者 100% 一致。
- 验证：`R.java` `menu_chapter_btn=0x7f08026c` 现已与 `public.xml` 一致；`more_action_menu_btn/ok_btn` 仍为 0x7f08026e/26f（与 public.xml 一致，未被改动）。
- 教训：**此类 apktool 反编译工程，每次改资源 id 后必须保证 `R.java` 与 `public.xml` 的 id 值完全一致**；对齐方向应"以 public.xml（打包真实映射）为准校正 R.java"，而不是凭记忆写值或反向改 public.xml。对齐后重跑 `build.sh` 即可，apktool 会保留 public.xml 的固定 id。
- 状态：代码层已彻底对齐，需重跑 `build.sh` 重新打包验证。

## 视频播放页「更多操作」接线（修正：真实播放页是 PlayerActivity→bl/xh 链，不是 VideoDetailActivity）
- 需求：在视频播放页按「更多操作」设置响应——菜单键模式：点击[菜单]键呼出右侧菜单；确定键模式：长按[确定]键呼出右侧菜单。
- 关键纠正（用户反馈）：`VideoDetailActivity` 是**视频详情页**，不是播放页；真实播放页 `PlayerActivity`（仅 smali，无反编译 Java）把按键完全委托给 `bl/xh.a`(DOWN)/`bl/xh.b`(UP)，链路由 `bl/xe.a()` 构建为 `xi→xp→xl→xw→xk→...`，OK 键播放/暂停在链头 `xi.g()` 的 `T()` 处被消费，故长按[确定]拦截必须落在 `xi.g()`（UP）层，`xi.f()`（DOWN）只记录按下时刻防双重触发。
- 实现（在播放器链内做，不碰 Activity）：
  - `bl/xi.java`（链头）：
    1. `import bl.abd;`、新增 `import android.os.Handler;`、`import android.os.Looper;`（`import bl.xh;` 之后）。
    2. 字段：私有 `Handler moreActionHandler = new Handler(Looper.getMainLooper())`、`boolean moreActionOkLongFired`、`Runnable moreActionOkLongRunnable`（run 里置 flag 并调 `showPlayerRightMenu()`）。
    3. `f()`(DOWN) 顶部：确定键模式且 `repeatCount==0`（首次按下）时 `removeCallbacks` 旧定时器、`moreActionOkLongFired=false`、`postDelayed(runnable, 500)`——**按住满 500ms 即在按住过程中**呼出右侧菜单（不等松手）。
    4. `g()`(UP) `switch` 前：确定键模式先 `removeCallbacks`；若 `moreActionOkLongFired` 为真（按住过程中已弹出）→ return true 吞掉松手、避免触发播放/暂停；否则（短按）落入 `T()` 照常播放/暂停。
    5. 新增私有 `showPlayerRightMenu()`：沿 `next()` 遍历链，命中 `xw` 实例则调其 `public d(true)` 呼出右侧菜单。
  - 反馈修正：原写法把长按判定放在 `g()`(UP)，导致菜单只在松手后才弹；改为 DOWN 阶段 `Handler.postDelayed` 触发后，菜单在**长按过程中**即弹出（与 `MoreActionKeyHandler` 长按模式一致）。
  - `bl/xw.java`（播放器控制器，持有 PlayerMenuRight）：`g()`(UP) 的 `KEYCODE_MENU` 分支加守卫 `if (abd.get_more_action_key(p()) != abd.MORE_ACTION_OK) d(!R());`——OK 模式下菜单键不再呼出右侧菜单（return true 吞掉），菜单键模式保持原 toggle 行为。
  - 取值：`bl.abd.MORE_ACTION_MENU=0`(默认)/`MORE_ACTION_OK=1`；`p()` 返回 Context，`get_more_action_key(p())` 可用。
- 行为：菜单键模式=菜单键呼出右侧菜单（恢复原版标准行为）；确定键模式=长按OK(≥500ms)呼出右侧菜单、菜单键对该动作失效。短按OK 在两模式都照常播放/暂停。两模式互斥。
